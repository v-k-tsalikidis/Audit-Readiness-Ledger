# Meltemi Logistics — example document set

Meltemi Logistics does not exist. The company, the depot, the systems and
the people in these documents are invented. Nothing here comes from any real
organisation, and nothing comes from the author's own service. You can read,
copy and change any of it.

The set is here so that the first command you run against this tool shows
you what it does, on documents you can open and check, instead of asking you
to supply your own confidential policies to find out.

```bash
audit-readiness-ledger examples/meltemi-logistics/documents
```

## What it is meant to be

A small freight company that has written down some of its information
security, the way a small company actually writes it down: eight or nine
documents, some careful and some rushed, a scanned PDF nobody converted, and
a text file of operational notes that is not a policy at all but is sitting
in the same folder.

The documents live in `documents/`. This README sits outside it, because
anything inside the folder you point the tool at is read as a document, and
notes about the example set are not part of the example set.

## What is deliberately wrong with it

Every one of these is planted. They are what the checks are for, and
`tests/test_example_set.py` asserts the tool still finds each one, so a
change that quietly breaks a check fails the build.

| Where | Planted defect | What should report it |
| --- | --- | --- |
| `incident-response-plan.md` | No document owner, only an approver | Document hygiene, fields not filled in |
| `backup-and-recovery-procedure.md` | Review date of 2025-03-01, long past | Document hygiene, reviews that are overdue |
| `acceptable-use-and-remote-working.md` | Review date written `05/03/2027` | Document hygiene, dates that need rewriting |
| `information-security-policy.md` | Cites a Human Resources Security Standard that is not in the folder | Documents referred to but not supplied |
| `logging-and-monitoring-sop.docx` | Cites a Records Retention Standard that is not in the folder | Documents referred to but not supplied |
| `supplier-security-standard.pdf` | A scan, not text | Files that could not be read |
| `operations-notes.txt` | Says vulnerability scanning has not started and there is no change management standard | Controls a person should read, flagged as deferral language |
| `operations-notes.txt` | Not a policy, so it has none of the control fields | Document hygiene, fields not filled in |

The last two are the interesting pair. A document that names a subject and
then says the organisation does not do it must not count as coverage — that
would take a real gap off the gap list. The tool reports it as something a
person has to read, and says why.

## What is deliberately right with it

Most of the set is ordinary and complete, because a fixture where everything
is broken tests nothing. Access control, incident response, physical
security, asset management and logging are all written up with a full
document control block, and the report shows them as subjects the set speaks
to — which is not the same as saying the controls are met, and the report
says so in its own words.

## What is deliberately absent

There is no screening policy, no awareness training, no secure development
standard, no threat intelligence and no formal change management. Those
controls have signatures in the lexicon and no document to match, so they
appear in the gap list. That list is the point of the tool.

## The .docx

`logging-and-monitoring-sop.docx` is a real Word file, not Markdown with a
different extension. It carries its document control block in a table, which
is where policies really put it, and it exists so the Word reading path and
the paragraph-based citations are exercised on every run rather than only in
unit tests. It is regenerated by `scripts/build_example_docx.py`.
